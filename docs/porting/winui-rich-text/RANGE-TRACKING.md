# Independent range tracking during SetText

Explicit plain `RichEditTextRange::set_text` now carries the accepted replacement
span through the shared document/editor transaction. Existing independent ranges
track that replacement as endpoint pairs. Ordinary `TextPointer`, public document
change records and other edit origins retain their existing policies. This is a
bounded consumer of measured system-MSFTEDIT behavior; the complete native range
engine and packaged WinUI engine remain unverified.

## Evidence and scope

The immutable [x64](native-msftedit-e5a0778a-x64.json) and
[ARM64](native-msftedit-e5a0778a-arm64.json) records contain the observations.
Both measured checkout `87aa7390668cf0450e18c4f3f7839df5db22ccd1` at workflow
head `e5a0778a9be45d82e9915c985fc835b575bdf337`, using probe blob
`64262e70bb48d4241fbe4626d27df85c388284ba`. Archive length, SHA-256 and member
CRC verification, runner/engine versions and extraction provenance are retained
in those records and [TESTS.md](TESTS.md).

The consumer combines 115 successful external `SetText` edits from the original
independent Gravity family with 15 successful edits from the separate passive
range family. Each edit observes a primary range and its independent duplicate:
130 edits, 260 after-pairs. All represented observations agree between x64
MSFTEDIT 6.2.26100.33648 and ARM64 MSFTEDIT 6.2.26100.9278.

[`rich_edit_text_range_tracking_native_cases.rs`](../../../src/FerroUI.Controls/rich_text/rich_edit_text_range_tracking_native_cases.rs)
retains literal requested ranges and modes, before/after primary and duplicate
states, acted edit spans, UTF-16 input lengths, HRESULTs, resulting acted ranges
and complete native stories. An independent review compared all 1,690 represented
values against the recorded source; expected endpoints are not generated by the
Rust mapping function. Each fixture begins in a fresh control containing
`abcdef`; the native story getter also returns its terminal paragraph marker.
The public FerroUI getter applies its existing terminal-marker projection.

A source-derived audit of the prior generic pointer policy disagreed on 90 of
the 260 after-pairs, across 45 edits. That count is a simulation against the
record, not a claimed execution of the older Rust test binary. Compilation and
execution of the new literal replay and framework regressions are recorded at

## Why the operation span must survive

For a passive range `1..4` in `abcdef`, these recorded operations distinguish
the original replacement from the minimal visible text difference:

| Accepted operation | Resulting text | Passive range afterward |
|---|---|---|
| Insert `X` at `2..2` | `abXcdef` | `1..5` |
| Replace `0..2` with `abX` | `abXcdef` | `3..5` |
| Insert `X` at `0..0` | `Xabcdef` | `2..5` |
| Replace `0..2` with `Xab` | `Xabcdef` | `3..5` |

The first two operations share one minimal string difference, as do the last
two. Reconstructing the intended operation from the final string loses the
distinction. Changing ordinary pointer gravity would also affect unrelated
selection, input, clipboard and layout behavior without evidence for those
origins.

The accepted span belongs to the range command. It is recorded after editor
acceptance and normalization, with the actual UTF-16 length inserted. It is
private bookkeeping: public `DocumentTextChange` values continue to describe
the visible minimal replacement and public batches retain their existing
notification semantics.

## Measured pair rules

[`RangePosition`](../../../src/FerroUI.Controls/rich_text/rich_edit_text_range_tracking.rs)
holds the two positions together. The original endpoint affinities are retained
for later edits that do not have the measured origin. Formatting
[`RangeGravity`](RANGE-GRAVITY.md) remains separate metadata.

The following describes the bounded mapper. Coordinates refer to the pre-edit
document; the insertion length and removed span determine the shift afterward.

| Relation to the accepted edit | Pair behavior |
|---|---|
| Caret at or before the edit start | Keep the caret before the edit. |
| Caret inside a replacement or at its end | Collapse to the edit start. |
| Caret after the edit end | Shift by inserted length minus removed length. |
| Nonempty range ends at or before the edit start | Keep both endpoints. An insertion at the range end remains outside it. |
| Nonempty replacement ends at or before the range start | Shift both endpoints. |
| Insertion before a nonempty range | Shift both endpoints. |
| Insertion at the start or inside a nonempty range | Keep its start and extend its end. |
| Replacement exactly equals the nonempty range | Adopt the inserted span. |
| Replacement otherwise covers the whole range | Collapse to the edit start. |
| Replacement overlaps the range's beginning | Start after the inserted text; shift the surviving end. |
| Replacement overlaps the range's end | Keep the surviving start and end at the edit start. |
| Replacement lies within the range, possibly sharing one endpoint | Keep its start and adjust its end by the length change. |

These rules are implemented once. Tests call the real range/editor/document
pipeline and compare against literal observations. They do not duplicate the
mapper as an expected-value calculator.

## Integration with FerroUI transactions

The public facade uses the existing editor transaction, format resolver, input
acceptance, history and independent editor-selection restoration. A private
`insert_range_text` path reaches `RichTextDocument::replace_range_text`.
Ordinary programmatic edits, `TypeText`, rich fragments, composition and snapshot
restoration do not acquire this origin merely because they run inside that
transaction. In particular, deleting through an empty rich snapshot uses its
original generic origin even though it shares the plain deletion helper.

The document installs a one-shot operation description immediately around the
accepted Run splice or completed structural installation. It includes the old
observed-text identity, expected mutation version, original byte/UTF-16 span,
accepted inserted string and eligible paired listeners. Observation validates
the entire resulting splice against that description. A string that merely has
the same length or prefix is insufficient. A scope guard retires only its own
pending description, so an early return cannot leave an origin for a later edit.

Eligible paired listeners are captured before the tree changes. A range created
by a property, tree or virtual text-read callback already addresses the state
it observed and cannot receive an earlier operation. Generic-origin listeners
are similarly captured before virtual text reads. Coordinate updates occur
immediately for each accepted replacement, including inside a notification
batch; coalescing public events does not coalesce the pair transformations.

Each range's coordinate pair is a `Cell` behind `Rc`, with weak subscriptions
and a semantic generation counter. Private bookkeeping does not borrow the
facade's `RangeData`, call application code or keep either a range or document
alive. Dropping the owned tracker disposes its internal subscription. Explicitly
changing endpoints creates a new coordinate identity, while a shared clone
retains the same range object and `get_clone` creates an independent one.

## Callback ownership and observation order

Text and formatting reads can enter application code through FerroUI's virtual
inline/block interfaces and property notifications. Three boundaries require
specific treatment:

1. **A virtual text read writes newer content.** The observation's mutation
   version is checked before replacing the canonical observed text. A stale
   outer read cannot publish an invented replacement over the nested write.
   The accepted nested mutation owns both its content and current positions.
2. **A Run property callback writes before or after parent invalidation.** The
   full-splice match and final setter mutation fence distinguish the accepted
   outer splice from newer callback work. A proven interruption returns the
   existing reentrant-edit error and advances the editor's external ownership,
   preventing an older grouped rollback from restoring over callback content.
3. **Field reconciliation enters a virtual reader.** Both private coordinate
   channels and the accepted public change queue advance before semantic field
   reconciliation. A nested edit therefore starts from the accepted coordinate
   state. The existing notification batching policy remains in place; this does
   not establish global atomicity for arbitrary direct tree writes that reenter
   reconciliation outside an edit batch.

The field and pointer changes serve the existing shared model; they do not
introduce a second document, independent event queue or native compatibility
object graph. Regressions exercise real custom Run/Inline callbacks, public
notifications and link-field reconciliation.

## Failed groups and successful history

A covering replacement can collapse a passive range and discard its old extent.
Reversing a visible string difference cannot reconstruct those endpoints. The
existing outer edit group therefore captures weak paired-position checkpoints
before the transaction. After successful document rollback, and before public
publication, it restores only the same live coordinate identities that
participated in a paired mutation.

The generation advances even when a semantic edit leaves a pair numerically
unchanged: generic restoration can still move it. Explicit endpoint replacement
creates a new identity, so it is excluded from the older paired checkpoint.
That newer identity still follows the existing generic snapshot-restoration
policy; its numerical offsets are not frozen during rollback. Newly created
or dropped ranges are not resurrected. A callback-owned
model change retires the older group through the existing external-change
generation and prevents restoration of its paired checkpoint.

This is a stated FerroUI transaction policy. Successful Undo/Redo retains the
existing generic snapshot-restoration policy; no native paired history behavior
is inferred from the single-edit fixtures. Existing mode/format ownership and
the distinction between shared and independent clones remain intact.

## Verification boundaries

[`rich_edit_text_range_tracking_tests.rs`](../../../src/FerroUI.Controls/rich_text/rich_edit_text_range_tracking_tests.rs)
contains two native replay definitions and seventeen framework regressions.
The latter cover accepted scalar-safe input, structural normalization, distinct
origins with equal visible differences, immediate batched updates, rollback,
new identities, callback ownership, rich-fragment deletion and weak lifetime.
They establish FerroUI behavior rather than adding native observations.
Compilation, focused execution and full Controls results are recorded separately
at their actual source checkpoint in [TESTS.md](TESTS.md).

The measured scope leaves these contracts open:

- The actual selection and `TypeText` duplicates use a distinct native path.
  Measured supplementary-character and CRLF cases already distinguish that path
  from this plain `SetText` law; [RANGE-GRAVITY.md](RANGE-GRAVITY.md) retains it as
  a separate boundary.
- Native formatting caches for untouched independent duplicates need experiments
  controlling the first font/paragraph read. The endpoint fixtures themselves
  read formatting and therefore cannot settle that cache behavior.
- A replacement with no visible text difference emits no private pair event.
  The recorded exact same-text case agrees, while other overlapping same-text
  replacements remain unmeasured.
- Paragraphs, fields, embedded objects, supplementary characters in the initial
  source, structural/synthetic terminal positions, repeated edit sequences,
  native history, callback semantics and arbitrary direct tree mutation need
  their own native evidence. Framework tests do not establish that parity.
- The source repository contains the host and documented interfaces rather than
  the complete external WinUI editing engine. System-MSFTEDIT agreement does
  not complete that missing implementation boundary.

The affected file/API entries remain partial or reference-only. No runtime
source file is promoted to complete by this bounded implementation.
