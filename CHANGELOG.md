# Changelog

All notable changes to FerroUI are recorded in this file. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). All crates of the workspace are released together at one version; a version with a pre-release identifier (`-preview.N`) is a preview, which may change any part of the public API. The release process is described in [docs/release.md](docs/release.md).

## [Unreleased]

### Added

- **WPF-style 3D, step D1: the Media3D values** (#608, [docs/porting/media3d.md](docs/porting/media3d.md), section 3.12): the new crate `ferroui-media3d` has WPF's `Point3D`, `Vector3D`, `Size3D`, `Rect3D`, `Point4D`, `Matrix3D` and `Quaternion` with double-precision components. `Matrix3D` keeps WPF's row-vector convention: `determinant`, `has_inverse`, `invert` (a `Result` with `Matrix3DError`), `append` and `prepend`, `rotate`, `rotate_at`, `scale`, `scale_at`, `translate` and their prepended forms, and `transform`, `transform_vector` and `transform_point4d` (a point is divided by its `w` under a projective matrix, a vector ignores the translation). `Quaternion` has `from_axis_angle`, `angle` in degrees, `axis`, `conjugate`, `invert`, `normalize`, `slerp` and `slerp_with_path`; `Vector3D` has `dot_product`, `cross_product`, `angle_between` and `normalize`; `Size3D` and `Rect3D` have WPF's `Empty`, and `Rect3D` its union, intersection, containment and offset, with negative sizes and changes of `Empty` refused by `Size3DError`. The operators are `std::ops` traits, and each value parses and writes WPF's text form in the invariant culture (`"0,0,5"`, `"1 2 3"`, `"Identity"`, `"Empty"`), which is also its markup converter (`ferroui_media3d::register_types`). The design of the whole port (the scene model, one WGSL shader for every backend, the fallback chain, and video frames as 3D materials) is in the same document; section 8 of the media specification now puts 3D scenes in scope.
- **Theme trimming is on by default** (#568, [docs/porting/theme-trimming.md](docs/porting/theme-trimming.md), section 11.8, [docs/binary-size.md](docs/binary-size.md), section 4.11). An application whose compiled markup constructs a theme (`<WinUITheme />`) now links only the units of the theme it needs without stating anything; `[package.metadata.ferroui] theme-trimming = false` turns it off, and `theme-roots` (names, or `"all"`) keeps its meaning. Validated on every desktop sample and the ControlCatalog page tour. Hello world's `dist` executable is 28.63 MB instead of 37.98 MB with the full theme.
- **Theme trimming roots what the compiled documents of the dependencies name, and `full-themes` replaces `type-tables` as the keep-all switch** (#568, [docs/porting/theme-trimming.md](docs/porting/theme-trimming.md), section 11.7). The `.xamlmeta` of a crate whose compiled markup has no theme units records the types and keys its documents name (`referenced_types`, `referenced_keys`), and an application that trims its themes roots them: a control library's template that names a key of the application's theme (`{StaticResource SplitViewPaneAnimationEasing}`) keeps the unit that defines it. `ferroui-base` has a new feature `full-themes` (which includes `type-tables`) for what can show any control (the run-time loader, hot reload, the designer, DevTools, Inspect, Diagnostics); its build script prints `full_themes=1`, read as `DEP_FERROUI_BASE_XAML_FULL_THEMES`, and the compiled themes' cfg is now `ferroui_full_themes`. `ferroui-view` and `ferroui-xaml-interactivity` keep `type-tables` only, so their applications trim.
- **Theme trimming roots from code** (#568 step 4, [docs/porting/theme-trimming.md](docs/porting/theme-trimming.md), section 11). The type models record the classes each class's code constructs: `ferroui-build-scan` reads `X::new(..)`, `X::new_..(..)`, `X::builder(..)` and `X::default()` (with a module path or a qualified type, in macro bodies too, outside test code, comments and string literals) in the file of a class and in its `impl` blocks, and writes them as `TypeModel::creates` (`"creates"` in the `.xamlmeta`, optional, so older files read as creating nothing). An application that trims its themes also roots them by its sources: `ScanOptions::source_references` collects the upper-case names and the string literals of its code (`Scan::references`), and `theme_roots::source_roots` keeps the names that are type keys or classes and the strings that are keys (`CalendarView::new()`, `"AccentButtonStyle"`). Every live type makes the classes it creates live, transitively (`theme_roots::TypeGraph`, which replaces `BaseClasses`). A control created only in code no longer needs a `theme-roots` entry; a name built at run time still does. Hello world keeps the same 30 of 164 WinUI units (28.63 MB `dist`).
- **Theme trimming in applications, opt-in** (#568 step 3, [docs/porting/theme-trimming.md](docs/porting/theme-trimming.md), section 10, [docs/binary-size.md](docs/binary-size.md), section 4.11). An application with `[package.metadata.ferroui] theme-trimming = true` in its manifest constructs the themes its documents construct from the units it needs. `ferroui-build` computes them from what the documents name (types with their base classes, and keys), the unit graph of the theme (references, `BasedOn`, the types templates construct) and the optional `theme-roots = ["Name", ..]` or `theme-roots = "all"`. It writes `compiled_markup::THEME_PARTS_<CLASS>`, and the emitter writes `<WinUITheme />` as `WinUITheme::with_parts(None, ..)`. New API: `with_parts(sp, parts)` on `WinUITheme`, `FluentTheme`, `SimpleTheme` and `MacOSTheme`, and in `rt` `ThemeParts`, `register_theme_parts`, `active_theme_units` and `report_trimmed_theme`. `Build::theme_roots` and `Build::type_tables` in `ferroui-build`. `ferroui-base` with `type-tables` prints `cargo::metadata=type_tables=1` (`DEP_FERROUI_BASE_XAML_TYPE_TABLES`), and such builds keep every unit. In debug builds the first lookup of a trimmed control theme logs `the WinUI control theme of <Type> was trimmed: add it to theme-roots`. `new()`, `with_service_provider()` and applications that do not opt in keep the full theme. Hello world opts in: its `dist` executable goes from 37.98 MB to 28.63 MB (macOS ARM64), keeping 30 of the 164 units of the WinUI theme, and looks the same as with every unit.
- **`ferroui_system::task::spawn_local_on_result`** (#567, [docs/porting/panics-as-exceptions.md](docs/porting/panics-as-exceptions.md), section 5.2): runs a future whose output, `Result<T, JoinError>`, is the outcome of its handle, so that a future ends its task with `JoinError::Panicked` or `JoinError::Canceled` without a panic. The page transitions of `ferroui-base` (`CrossFade`, `PageSlide`, `Rotate3DTransition`, `CompositePageTransition`) report the failure of an animation with it: the handle of `IPageTransition::start` ends with the same `JoinError::Panicked` (a `String` payload with the message) as before, without unwinding, so with `panic = "abort"` too.
- **Fallible OpenGL loading and making a context current** (#567, [docs/porting/panics-as-exceptions.md](docs/porting/panics-as-exceptions.md), section 5.5): `GlInterface::try_new`, `GlInterface::try_from_native_utf8_get_proc_address`, `GlBasicInfoInterface::try_new`, `GlContextInfo::try_create`, `EglInterface::try_new` and `Win32AngleEglInterface::try_from_loader` fail with an `OpenGlError` when a required entry point cannot be resolved, where the plain forms panic. The provided methods `IGlContext::try_make_current` and `IGlContext::try_ensure_current` fail when the context is lost or cannot be made current; the EGL, GLX, WGL, macOS native GL, EAGL and WebGL contexts implement them. The backends use these forms, so with `panic = "abort"` a driver without an entry point falls back to the next rendering mode and Skia releases a snapshot after a context loss without aborting. `Dispatcher::start_local_on_result_with_priority` starts a future whose `Err(JoinError)` fails its handle without a panic, and the samples' `mini_mvvm::start_async_on_result` wraps it; the page transitions of the control catalog use it.
- **`dist-unwind`** (#567, [docs/binary-size.md](docs/binary-size.md), section 4.7): the shipped build with unwinding, for an application that catches panics to carry on.
- **The tables of types are trimmed by default** (#566, [docs/binary-size.md](docs/binary-size.md), section 4.6). An application that loads only compiled markup no longer registers every crate's tables of classes and markup types at start-up. The crates of the framework register them with `TypeInfo::register_table`, `MarkupType::register_table` and `MarkupAssembly::register_table`, which do nothing without the `ferroui-base` feature `type-tables`, and the linker drops what only those tables reach: hello world's `dist` build goes from 50.78 MB to 45.28 MB, with the same start-up time. A type is still known once it is used (a class when it is initialised, the value types of registered properties, the classes a compiled document's reflection-binding paths name). The plain `TypeInfo::register_all`, `MarkupType::register`, `MarkupType::register_all` and `MarkupAssembly::register` always register, so an application's own types work with no change. Anything that looks types up by name keeps the tables through `type-tables`: the run-time XAML loader, the designer, DevTools, hot reload, Inspect, the declarative View API and the behaviors' member lookup; an application that looks types up by name itself enables it.

- **`{x:Bind}` in FerroUI XAML, compiled** (X0 and X1 of #525, [docs/porting/x-bind.md](docs/porting/x-bind.md)): `x:Bind` is one markup extension of the XAML runtime library, `XBindExtension` (`{x:Bind ...}`, or `{XBind ...}` in the framework namespace), which the XAML compiler builds for the run-time loader and the Rust emitter alike. Its path is a compiled path of typed accessors resolved against the root of the document, or, inside a `DataTemplate`, against the template's `x:DataType`; it reads properties, attached properties and named elements (`editor.Text`). The default mode is `OneTime`; `OneWay` and `TwoWay` follow change notification, with `UpdateSourceTrigger` (`LostFocus` by default for `TextBox.Text`). `XBindings`, one per root (`XBindings::get_for_root`), is WinUI's generated `Bindings` object: `initialize`, `update` (re-reads `OneTime` bindings), `stop_tracking`, `diagnostics`; a document root is initialized when it is attached to a visual tree, the counterpart of WinUI's `Loading`, and a template instance reads its item whenever its data context changes. An unresolved path, a `TwoWay` path that cannot be written, a mode or update trigger WinUI rejects, a template without `x:DataType` and x:Bind in a style are compile errors of the emitter and load errors of the run-time loader, with the position. `CompiledBindingPath::build_expression` is public. Functions, casts, indexers, converters, events, `x:Phase` and the move of the WinUI importer onto this core are the next steps of the plan.
- **`{x:Bind}` paths of WinUI's grammar, functions and `BindBack`** (X2 of #525, [docs/porting/x-bind.md](docs/porting/x-bind.md)): the path of an x:Bind is parsed in the grammar of WinUI's compiled bindings (`BindingPath.g4`) and compiled in both back ends: static members (`local:Helpers.Prefix`), integer and string indexers (`Items[0]`, `Map['key']`), attached properties after a path (`editor.(Grid.Row)`) and interface members (`Model.(local:INamed.Name)`), casts of a whole path and inside a path (`(x:String)Tag`, `((local:Model)Tag).Name`), and functions at the end of a path, on the root (`Format(Title)`), on a path (`Model.Greet(Title, 'text', 3)`) and static (`local:Helpers.Join(Title, '-', 2)`), with path arguments and literals (`x:True`, `x:False`, `x:Null`, numbers, quoted text). A `OneWay` function is called again when one of its argument paths changes and when its owner raises `PropertyChanged` with its name; a `TwoWay` binding through a function writes back through `BindBack` (`BindBack=ParseTitle`, `BindBack=Model.Rename`, `BindBack=local:Helpers.Store`). The engine has the function element `CompiledBindingPathBuilder::function` and `bind_back` (`PathFunctionArgument`, `PathFunctionInvoke`, `PathBindBack`, `CompiledBindingPathElementKind::Function`, `FunctionNode`); `XBindExtension` has `BindBack`; generated code calls `rt::path_function`, `rt::path_static_function`, `rt::path_bind_back`, `rt::path_static_bind_back` and `rt::path_key_indexer`. The markup extension scanner keeps `()` and `[]` of the path of x:Bind together, as WinUI's does. An unknown function, a member that is not a function, the wrong number of arguments, an argument of the wrong type, a return type the target does not accept, a function that is not at the end of the path or is an argument, a `TwoWay` function without `BindBack` (or `BindBack` without one, or of the wrong method), `TwoWay` after a cast, an impossible cast and an indexer on a type without one are compile errors and load errors with WinUI's messages and the position.
- **`{x:Bind}` converters, fallback values and target null values** (X3 of #525, [docs/porting/x-bind.md](docs/porting/x-bind.md)): `XBindExtension` has `Converter` (an `IValueConverter`, given as a `{StaticResource}`), `ConverterParameter`, `ConverterLanguage` (a language tag, the `CultureInfo` the converter is called with), `FallbackValue` (the value of the target when the path cannot be read: a null in its middle, a failure) and `TargetNullValue` (when its value is null), in both back ends; they are the options of the engine's expression, so a `TwoWay` binding writes back through `ConvertBack`. A path that cannot be read is not a diagnostic of `XBindings` when the binding has a fallback value. `ConverterParameter` or `ConverterLanguage` without a converter, a converter with a function, a converter that is a resource of the document of another type than `IValueConverter`, `TargetNullValue` on a target that cannot be null, a fallback or target null value that is not a text or `{x:Null}`, and a text that cannot be converted to the type of the target are compile errors and load errors with WinUI's messages and the position.
- **`{x:Bind}` event binding** (X4 of #525, [docs/porting/x-bind.md](docs/porting/x-bind.md)): an event bound with x:Bind calls a method, on the root (`Click="{x:Bind OnClick}"`), on the value of a path (`Click="{x:Bind Model.OnClick}"`) or static (`Click="{x:Bind local:Handlers.OnClick}"`), for routed events and for the events metadata declares with their subscription, in both back ends. The method takes the event's arguments, base types of them, or no parameters, as WinUI's `BoundEventAssignment`; its owner is read from the root source when the event is raised (a null on the path calls nothing). The handler is subscribed when the bindings of the root are initialized (a template instance when it gets an item) and released by `stop_tracking`: `XBindings` holds the event bindings and their `Subscription` guards (`event_binding_count`, `subscribed_event_count`), and a failure of the method is one of its `diagnostics`. The engine has the element `CompiledBindingPathBuilder::event_handler` (`PathEventHandler`, `PathEventHandlerInvoke`, `CompiledBindingPathElementKind::EventHandler`) and `CompiledBindingPath::event_handler` and `read_once`; `XBinding` has `bind_routed_event` and `bind_markup_event`; generated code calls `rt::path_event_handler`, `rt::path_static_event_handler`, `rt::x_bind_routed_event` and `rt::x_bind_event`. An event bound to what is not a method, an unknown or overloaded method, a method of another signature, a method in the middle of the path, a call, and a mode, update trigger, converter, substitute value or `BindBack` on an event are compile errors and load errors with WinUI's messages and the position.
- **`{x:Bind}` directives, phases, `x:Load`, control templates and windows** (X5 of #525, [docs/porting/x-bind.md](docs/porting/x-bind.md)): in both back ends, `x:DefaultBindMode` gives the x:Bind bindings of an element and its subtree their mode when they name none (the nearest wins; `OneTime` without one; an event binding has no mode). `x:Phase` on an element of a typed `DataTemplate` makes a container read its bindings in that phase: `XBindings` implements the phasing contract `IDataTemplateComponent` and is the template component of the root of each instance (`XamlBindingHelper.DataTemplateComponent`); phase zero takes the item from the container, the later phases show their elements (hidden until then, and again when the element is recycled) and read their bindings, and the repeater's `Phaser` drives it. `x:Load="False"`, `x:DeferLoadStrategy="Lazy"` and a bound `x:Load` (`x:Load="{x:Bind IsShown, Mode=OneWay}"`) defer the creation of an element: a `DeferredElement` placeholder holds its place, and the element is built (with the root, the item or the templated parent its bindings read, and a name scope of its own) when `Load` becomes true or `DeferredElement::find_name` asks for it, and released when `Load` becomes false; a bound `x:Load` in a control template loads from the templated control (the fix of microsoft-ui-xaml #12239). x:Bind in a `ControlTemplate` with `TargetType` reads the templated control, of that type (`XBindExtension::target_type`), and a `Window` document initializes its bindings when the window is activated. The phasing contract `IDataTemplateComponent` moves from `ferroui-controls-repeater` to `ferroui-controls::templates` (re-exported where it was), with WinUI's `XamlBindingHelper`; `RepeaterBindingHelper.DataTemplateComponent` is that property. An invalid `x:DefaultBindMode`, `x:Phase` outside a `DataTemplate`, without an x:Bind or not below 25, `x:Load` with another value, without `x:Name`, with `x:DeferLoadStrategy`, on the root of a document or of a template or on a resource, an invalid `x:DeferLoadStrategy`, and x:Bind in a `ControlTemplate` without `TargetType` are compile errors and load errors with WinUI's messages and the position.

- **`{x:Bind}`: the accessor of a class document, populated and reloaded roots, the gallery, migration notes** (X7 of #525, the last step; [docs/porting/x-bind.md](docs/porting/x-bind.md) sections 3.13 and 8): the Rust emitter gives a class (`x:Class`) whose document uses x:Bind an accessor of the bindings of its root, `MyPage::bindings() -> Option<Rc<XBindings>>` (WinUI's `this.Bindings`, a thin method over `XBindings::get_for_root` in the generated class file; a document without x:Bind adds no API). `XBindings::update_populated(root)` is what a root needs after a document populated it again or populated it while it is live: initialized bindings are read again (`Update`, `OneTime` included), the bindings of a root already attached to a visual tree (or of an active window) are initialized, any other root waits for its attach; the run-time loader calls it after it populates a root instance, so a designer or a reload that populates a live root shows the new markup. They give a `JoinHandle`; the dispatcher aborts its tasks when it shuts down (their outcome is `JoinError::Canceled`), also the ones spawned afterwards. `invoke_async_task*`, `DispatcherTaskScheduler` (`spawn`, `spawn_local`, `start_local`), `resume`, `yield_now` and `await_with_priority` run on it, with the same signatures and behaviour; `DispatcherTask` keeps its contract. `ferroui_system::task` gains `spawn_on(create, schedule)` (a task spawned from any thread onto a schedule), `AbortHandle` (`JoinHandle::abort_handle`), `Id` (`JoinHandle::id`, `try_id()` for the task being polled), `poll_now(id)` (polls a task of the thread inside the caller, for a continuation moved to another priority) and `Schedule::spawned`, a provided method through which a schedule is told of its tasks.
- **The executor core: `ferroui_system::task`** (A1 of C4, #423, [docs/idiomatic-rust-async.md](docs/idiomatic-rust-async.md), section 3): one task table and poll loop per thread, named after `std::task`. `spawn_local(future)` runs a future as a task of the current thread with the rule of `threading::tasks` (polled at once, again inside the call that wakes it on its thread, after its own poll when the wake comes from inside it; a wake from another thread waits for `run_pending` or `block_on`, and is announced to the thread's schedule), `spawn_local_on(future, schedule, FirstPoll)` gives a task a `Schedule` (a `Send + Sync` trait, implemented by closures, that queues each poll on the task's thread; one queued poll at a time; a queued poll that runs inside the task's own poll schedules it again after that poll), `set_thread_schedule`, `run_pending` and `block_on` (which raises the panic of its future again). Spawning gives a `JoinHandle<T>`: a future of `Result<T, JoinError>`, `is_finished`, `abort` (drops the future on its thread; the outcome is `JoinError::Canceled`), `Send` when `T` is; dropping it detaches the task. `JoinError` is `Canceled` or `Panicked(Box<dyn Any + Send>)` (`into_panic`, `try_into_panic`, `resume_unwind`, `std::error::Error`). `JoinHandle::shared` gives `Shared<T>` (`T: Clone`) for several observers, whose `on_finished` continuations run before the awaiting futures are woken. `threading::tasks` (`Task::spawn_local`, `spawn_local`, `block_on`, `run_pending_wakes`, `set_thread_poster`, `run`) now runs on it, with the same signatures and order of continuations; nothing is deprecated in this step.

### Changed

- **Control themes as declarative tables** (#568 step 5, [docs/porting/theme-trimming.md](docs/porting/theme-trimming.md), section 12). The Rust emitter writes the factory of a `ControlTheme` as a static `rt::ControlThemeTable` (target type, `BasedOn` as `{StaticResource}`, setters, nested styles and control templates, in document order) and one call of `rt::build_control_theme`, which makes the calls of the statements it replaces in the same order, with the same errors at the same positions. Setter values are data when they are constants, `{DynamicResource}`, `{StaticResource}` or a control template; any other value becomes a function of its factory with the statements the emitter wrote for it, so each factory keeps its own table and units stay separately removable. A factory with a member the table does not hold (animations, a resource dictionary, the name scope) keeps its native code. Selector chains are static slices of `rt::SelectorStep` interpreted by `rt::build_selector`, one static per distinct chain, and each property definition the tables name is one function per generated function. The run-time choice of the setter of a `{StaticResource}` value (the `is_instance` chain) is one call of `rt::assign_resource_value` with an `rt::ResourceChoice`, a non-generic choice and one typed assignment per property value type, and consecutive `{TemplateBinding}`s on one object are one call of `rt::bind_template_bindings` over a table; templates otherwise stay native code. The checked-in compiled markup of the themes and the emitter fixtures are regenerated.
- **Type checks no longer keep whole classes in the executable** (#612, [docs/binary-size.md](docs/binary-size.md), section 4.12). `is::<T>()`, `cast::<T>()` and `downcast_ref::<T>()` compare a per-class identity (`TypeIdentity`, `ObjectType::IDENTITY`) instead of `T::TYPE`, whose initialisation, constructor and markup metadata every type check kept linked. The answers are the same. A theme-less window (release, macOS) goes from 41.76 to 38.64 MB.
- **`dist` builds without unwinding** (#567, [docs/binary-size.md](docs/binary-size.md), section 4.7): `panic = "abort"`. Hello world's executable is 21 % smaller (45.28 MB to 35.71 MB with the tables of types trimmed). A panic ends the process after the panic hook has run. No production path of the framework carries an expected error as a panic ([docs/porting/panics-as-exceptions.md](docs/porting/panics-as-exceptions.md)). `dist-unwind` is the shipped build with unwinding. `release` keeps unwinding. The development tools that isolate the application they inspect (the Designer, the previewer, hot reload, DevTools) are built with `dev`, `release` or `dist-unwind`.
- **OpenGL and Vello without catching panics** (#567, [docs/porting/panics-as-exceptions.md](docs/porting/panics-as-exceptions.md), section 5.5): `WglPlatformOpenGlInterface` logs the error of a context that cannot be created and no longer catches a panic. `WglContext::try_make_current` returns the loss of the context as an error instead of panicking. `BrowserWebGlRenderTarget::new` and `WebGlContext::new` return `Result<_, OpenGlError>`, and a WebGL target whose context cannot be used is left out with the error logged. The generated tables of entry points no longer check their required entry points twice: `ExternalObjectsOpenGlExtensionFeature` reports a missing one with its Rust name, as the other tables do. Vello refuses a `CombinedGeometry` of paths whose coordinates are not finite before the third-party sweep (the combination is empty, as when the sweep gives up), and leaves the swap chain of a lost device instead of releasing it.
- **Compiled themes are partitioned into units, with their graph in the `.xamlmeta`** (#568 step 2, [docs/porting/theme-trimming.md](docs/porting/theme-trimming.md), section 9). The Rust emitter partitions the compiled markup of a class whose documents merge other documents (`MergeResourceInclude`) into units: each merged control or resource document is a unit, and the ambient unit (index 0) holds what is always kept (the documents that are not merged, with the global styles, the hosts the framework creates, `CompactStyles` and `SystemAccentColors`). The entries of a unit are written as runs, functions that only the unit's `rt::ThemeUnit` refers to, and the build of each dictionary applies them where the entries were, through the static table of all units `THEME_UNITS` of the generated file (`rt::apply_theme_unit`), so `WinUITheme::new()`, `with_service_provider()` and the loader table build the same dictionaries as before. The `.xamlmeta` of the crate gains `theme_units`: for each unit its name, index and documents, the keys and type keys it defines, the keys it references and the types it constructs or selects (the key graph of #496's resource roots, re-implemented and extended with types). The checked-in compiled markup and `.xamlmeta` of the themes are regenerated. The WinUI theme has 164 units; hello world's `dist` executable grows by 0.25 MB until step 3 trims the units an application does not reach.
- **Automation providers return `AutomationError` for the calls the state of their element refuses** (#567, [docs/porting/panics-as-exceptions.md](docs/porting/panics-as-exceptions.md), section 5.4): the new `ferroui_controls::automation::AutomationError` (`ElementNotEnabled`, `InvalidOperation`, `ArgumentOutOfRange`, `NotSupported`; `From<ElementNotEnabledError>`) is the error of `IRangeValueProvider::set_value`, `IScrollProvider::scroll` and `set_scroll_percent`, `ISelectionItemProvider::add_to_selection`, `remove_from_selection` and `select`, `IExpandCollapseProvider::expand` and `collapse`, and `IToggleProvider::toggle`, which returned `Result<(), ElementNotEnabledError>`; an implementation changes its signature to `Result<(), AutomationError>`, and `ensure_enabled()?` still converts. The peers that refused a call with `panic!` (a read-only progress bar, a scroll viewer asked to scroll a direction it cannot scroll or to an out-of-range percentage, a radio button, a menu item without a submenu, a combo box that is not editable, a calendar, a TreeDataGrid row or read-only check box cell) return the error instead, so a screen reader query no longer ends an application built with `panic = "abort"`. The Windows UI Automation bridge and the WinUI proxies answer the result code of the original's exception (`UIA_E_ELEMENTNOTENABLED`, `COR_E_INVALIDOPERATION`, `COR_E_ARGUMENTOUTOFRANGE`, `COR_E_NOTSUPPORTED`) where they answered `E_FAIL`; `IValueProvider::set_value` keeps `ProviderError`, which carries the `AutomationError`.
- **Theme resources as row tables** (#568 step 1, [docs/porting/theme-trimming.md](docs/porting/theme-trimming.md), section 8). The Rust emitter writes a run of theme resources of one shape added to one dictionary as a static table of rows and one call of the builder of the shape in `rt`, instead of a build function per deferred resource and a statement per plain value: resource aliases (`{StaticResource Key}` alone), `SolidColorBrush`es with a literal colour, bound to a dynamic resource or whose colour is a static resource (`rt::add_resource_aliases`, `add_literal_brushes`, `add_dynamic_brushes`, `add_static_brushes`), and numbers, thicknesses, corner radii, colours and texts (`rt::add_double_resources`, `add_thickness_resources`, `add_corner_radius_resources`, `add_color_resources`, `add_string_resources`). The checked-in compiled markup of the themes is regenerated: the WinUI theme goes from 6,265 generated functions to 815 (14.64 MB to 10.08 MB of text), and hello world's `dist` executable from 40.39 MB to 37.73 MB (macOS ARM64), with the same theme load time.
- **The error scope of the markup runtime no longer unwinds** (#567, [docs/porting/panics-as-exceptions.md](docs/porting/panics-as-exceptions.md), section 5.1): inside `ferroui_markup_xaml::xaml_error_scope::with_xaml_errors` (the fresh-root loads of `load_winui`, `parse_winui` and `parse_winui_as`), a member without an error channel that a load reaches (the build of a deferred resource, the resource contracts of `ResourceInclude` and `StyleInclude`, the build of template content) reports its `XamlLoadError` to the scope and goes on as if it had produced nothing; the run-time loader stops at its next node, and the scope returns the first error reported. The scope works the same with `panic = "abort"`; it no longer catches panics. Outside a scope nothing changes. New: `IDeferredContent::try_build` (a provided method; `Err(DeferredContentFailed)` when the content reported its own failure) and `ferroui_base::controls::DeferredContentFailed`; `ResourceDictionary::try_get_value` builds with it, and a deferred resource whose build failed is not found and stays deferred. Hidden from the documentation: `xaml_error_scope::report` and `has_error`.
- **One observer for untyped bindings** (#576, [docs/binary-size.md](docs/binary-size.md), section 4.10). The property store receives values from bindings, animations and markup through one observer over boxed values with the routes of the property, instead of a typed observer per value type; typed bindings keep their typed path. Hello world's `dist` build is 1.56 MB smaller (41.95 to 40.39 MB), with the property, binding and styling benchmarks within noise.
- **Fewer closures in the metadata of types** (#569, [docs/binary-size.md](docs/binary-size.md), section 4.9). An enumeration member is its numeric value (`MarkupEnumMember::get(&markup)` makes it; the field `get` is gone), and `MarkupType::find_enum_member_of` finds the member of a value. Casts and reference types register one typed function each, and the untyped routes of properties copy values through one function per type. - **The asynchronous members of the controls and platforms give a `JoinHandle`, and a panic of their task is a value** (A6 of C4, #423, [docs/idiomatic-rust-async.md](docs/idiomatic-rust-async.md), sections 3.2 and 4): `NavigationPage` (`push_async`, `pop_async`, `pop_to_root_async`, `pop_to_page_async`, `replace_async`, `push_modal_async`, `pop_modal_async`, `pop_all_modals_async` and their `_with_transition` and `_with_parameter` forms), `INavigation`, `PageNavigationExtensions` (`push_async_of`, `replace_async_of`, `push_modal_async_of`), `Window::show_dialog` and `show_dialog_typed`, `TopLevel::request_platform_inhibition`, `IPageTransition::start` (and `CrossFade::start_cross_fade`), `ICompositionGlContext::dispose_async` and `ICompositionGlTexture::dispose_async` of `ferroui-opengl`, and `mini_mvvm::start_async` of the samples give the `JoinHandle` of a task of the dispatcher, where they gave a `DispatcherTask`. - **The dispatcher is the schedule of its thread, and a task spawned in a job continues at its priority** (A5 of C4, #423, [docs/idiomatic-rust-async.md](docs/idiomatic-rust-async.md), sections 3.1 and 3.5, finding F3): a dispatcher installs itself as the schedule of its thread when it starts (`ferroui_system::task::set_thread_schedule`) and removes itself at its shutdown, so a task of `ferroui-system` woken from another thread, and a `CancellationToken::register_local` callback canceled on another thread, run in a dispatcher job at `Default` without `run_pending_wakes` (or `FerroScheduler::install_on_ui_thread`). ### Fixed

- **FerroBoard collates and searches with the browser's `Intl` on Emscripten, without ICU in the module**. The Emscripten build of FerroBoard.Core linked the ICU 68.2 port and embedded its whole data package (28.57 MB, 11.34 MB with gzip), and the browser ControlCatalog's module went from 16.2 to 29.6 MB with gzip, over the budget of the published site. As on the other platforms, which use their system locale services, the browser build now uses the engine's `Intl.Collator` (tertiary and secondary strengths as the sensitivities `variant` and `accent`, root and unknown locales as CLDR's root collation) and `Intl.Segmenter` (collation search over whole characters), through `text/locale_text/collation.js`; no ICU code or data is linked or embedded.
- **Magnifiers, the text cursor indicator and input methods follow the caret of FerroUI text controls on Windows** (#430, [docs/porting/win32-platform.md](docs/porting/win32-platform.md), section 8.3): the framework draws its own caret, and the caret of the system that assistive technology follows was the input method's, two pixels square at the lower right corner of the text cursor, never shown, and only while the window had an input context. The Windows backend now keeps the caret of the system on the text cursor of every text input client (TextBox and the controls built on it, RichEditBox, any client of the text input manager): one pixel wide and as high as the cursor at its top left corner, shown with a blank bitmap so it draws nothing, moved only when the cursor moves, made again for another height or window, mapped from a popup to the window that owns it, and destroyed when focus leaves text. VoiceOver and Orca get no caret moves yet: their text interfaces are follow-ups (section 13.7). Narrator does not read caret moves yet; #430 stays open for it.
- **Password text boxes stay confidential to input methods and automation**: a `TextBox` with a `PasswordChar` marks its input context sensitive. It also asks the platform for a password (or PIN) keyboard without suggestions, capitalization or multiple lines, and does so whether or not the password is revealed. Its automation peer exposes no value provider, no value and no children, and raises no value change events; a value provider kept from before the mask also reads no value.
- **The nullable markup metadata of a type declared for another value** (`this:` or `handles:`) is the `Option` of the represented value, not of the declaration marker.
- **A dispatcher task no longer loses its wakes when its poll pumps the queue** (F1 of [docs/idiomatic-rust-async.md](docs/idiomatic-rust-async.md), A2 of C4): a future started with `invoke_async_task*` or a `DispatcherTaskScheduler` whose poll ran a nested loop (a synchronous `invoke` at a priority other than `Send`, a pumping `DispatcherOperation::wait`, `push_frame`) in which something it awaited completed had its queued poll run inside that loop, where it found no task and left the task marked as scheduled: every later wake was swallowed and the task never resumed. The poll that runs inside the task's own poll now marks it, and the task is polled again at its priority once that poll has returned; a `resume_with_priority`, `yield_now` or `await_with_priority` whose job runs inside the poll of its task does the same.
- **A panic in a future of `ferroui-system` faults its task** (F2 of [docs/idiomatic-rust-async.md](docs/idiomatic-rust-async.md), A1 of C4): a future run by `threading::tasks::spawn_local` (`Task::spawn_local`) that panicked left through the call that woke it (often `TaskCompletionSource::set_result`), stayed `Running` for ever, and the other futures waiting for the same task were never woken. The panic is now caught: the task is `Faulted` with a `TaskWorkError` that holds the message of the panic, and the call that woke it goes on (the default panic hook still reports the panic). A future of `ferroui_system::task` ends with `JoinError::Panicked`. A panic after the task has its outcome (in a continuation that its end runs) still leaves through the waking call, and `block_on` still raises the panic of the future it runs. Code that relied on a panic inside a spawned future reaching its caller (a test asserting inside a spawned future) now has to observe the task (`result()`, `is_faulted()`).
- **LiveCharts2: the Cartesian charts match the upstream snapshots** (#442, [docs/porting/livecharts2.md](docs/porting/livecharts2.md)): the box series of a chart stand side by side in each category (`SeriesContext.GetBoxPosition`, `BoxMeasureHelper`) and are drawn as the source's `BoxGeometry` (whiskers from the box, no caps, the theme's dark outline, padding 5 and the theme's maximum width 60); an axis of a single value spans one unit width and an axis without data ten, before its labels and padding are measured; the separators take their step from the draw margin, with the source's 16 px labels and the theme's Cartesian label padding of 12, so a single-point axis no longer lays out dozens of separators; stacked step areas share their edges with the series below, with no unfilled cells; the series take the theme's MaterialDesign500 palette, line, step, range and polar lines the area at alpha 50 under them (a transparent fill is the source's `Fill = null`), stacked areas the full colour without a stroke or geometry, and a line series bounds its points, not the pivot.
- **Rich text: a paragraph break and its merge no longer add empty runs to the paragraph** (#439, [docs/porting/winui-rich-text.md](docs/porting/winui-rich-text.md) section 12): each break and merge of the same paragraph added two empty runs to it, so its inlines and its list of inheritance children grew with every edit and editing slowed down the longer it went on. The paragraphs a replacement makes keep one of each group of consecutive empty inlines (the one an offset resolves to). `FerroObject::inheritance_child_entries` (`testing` feature of `ferroui-base`) reads the length of the list for tests.

- **The hot-reload manifest is written with Cargo older than 1.93** (#444): `Build::hot_reload_manifest(true)` decided from `CARGO_CFG_DEBUG_ASSERTIONS` or a `-C debug-assertions` rustflag whether the target has debug assertions, and Cargo before 1.93 never passes that variable to build scripts, so a dev build on those versions (the workspace minimum is 1.89) wrote no manifest and code that reads `FERROUI_HOT_RELOAD_MANIFEST` with `env!` failed to compile. Without the variable the root of the profile now decides (`PROFILE`, else `OPT_LEVEL`), and for a profile rooted in `dev` the version of Cargo (`$CARGO -V`) says whether the absence means a profile that turned debug assertions off (1.93 and later) or nothing (older); an explicit `-C debug-assertions` rustflag still wins. A build that requests the manifest and whose configuration cannot be determined fails with an error naming the values it saw. With Cargo before 1.93 a custom profile that changes the `debug-assertions` it inherits follows its root ([docs/development/hot-reload.md](docs/development/hot-reload.md)); `scripts/hot-reload/profile_probe.py` also checks the pre-1.93 rule.
- **No stall on the first frame that draws acrylic** (#437, [docs/porting/gpu-rendering.md](docs/porting/gpu-rendering.md), "Pipelines made ahead of their first draw"): with a cold Metal shader cache, the first frame of Skia Graphite that drew an `AcrylicBrush` (the NavigationView pane, flyouts, menus) stalled 160 to 455 ms while Metal compiled its pipelines on the render thread. Effects are now registered for a prewarm (`effects::register_effect_prewarm`; the WinUI theme and `AcrylicBrush` register the two forms of the in-app acrylic, `ACRYLIC_PREWARM_EFFECTS`); after a frame, each composition target hands the effects it has not prewarmed to its render target (`IRenderTarget::prewarm`), which draws them once offscreen through the painting of the effect brushes. On Graphite the draws go to a recorder of their own whose pipelines compile on a thread of their own (`GraphitePrewarmContext`); on Ganesh the programs compile on the render thread between two frames; raster targets and Vello (whose pipelines are made up front) do not prewarm. `SkiaOptions::prewarm_effect_pipelines` (on by default) turns it off; `FERROUI_EFFECT_PREWARM=0` does for a measure, and `FERROUI_SLOW_FRAME_MS=<ms>` prints each frame that takes longer.
- **The Vello window surface draws no scene into a window of another size** (#476): the surface of a window drawn through `wgpu` (Windows, X11, Wayland) took the size of its frame from the live window, so a frame whose scene was laid out before a resize showed that scene with a strip of the frame before it; a frame of the scene's size would instead be stretched to the window by the swap chain (`DXGI_SCALING_STRETCH` of `wgpu` on DX12). While the window and the scene differ by more than a pixel of rounding the surface now reports itself not ready (`RenderTargetNotReadyError`), the compositor skips the frame and asks again with the next tick, and the frame of the new size comes from the platform's own render of the resize.
- **Windows renders the frame of a new size before the resize returns** ([docs/porting/win32-platform.md](docs/porting/win32-platform.md), #476): `WM_SIZE` laid the window out and the frame of the new size was rendered in the `WM_PAINT` that followed once the message queue was idle, as upstream does; until then the desktop showed the window at its new size with the frame of the old size in it, the rest uncovered. `WM_SIZE` now renders that frame at once and validates the client area, in every composition mode. Measured in the Windows 11 VM with captures of the desktop right after `MoveWindow`: the part of the window that differs from the settled frame fell from 25 to 89 % to about 1 % (the caret and the cursor) in the WinUI composition, DXGI and redirection modes.
- **Wayland: a configure is answered with a frame at once** (issue 476, cooperative resize): a window renders the frame of a new configure right away, so the buffer of the new size carries the acknowledgement of the configure without waiting for the next frame of the render loop, and a configure that changes only the state of the window (activation, a maximize of the same size) is acknowledged even when nothing else asks for a frame. Popups already did this.
- **No stretched frames in the DXGI mode of Windows while resizing** (#476): the swap chain is created with `DXGI_SCALING_NONE` (upstream leaves `DXGI_SCALING_STRETCH`), so a frame that lags the size of the window is shown at its own size from the top left corner until the frame of the new size, which `WM_PAINT` renders synchronously, is presented.
- **iOS resizes cooperatively** ([docs/porting/ios-platform.md](docs/porting/ios-platform.md), #476): a rotation or a split view change showed the old drawable stretched to the new bounds until the next tick of the display link. `layoutSubviews` now renders the frame of the new layout on the main thread and presents it with the Core Animation transaction that gives the view its new bounds (`presentsWithTransaction`), as the macOS backend does; the render thread draws every other frame.
- **Android tells the system a resize is drawn only when it is** ([docs/porting/android-platform.md](docs/porting/android-platform.md), #476): `surfaceRedrawNeededAsync` ran its `drawingFinished` before the next batch was committed, as upstream does, so after a rotation or a resize the system showed the frame of the old size stretched or cropped until the next frame. It now runs when the frame of the new size has been rendered, on the render thread, and the render loop is asked for that frame out of turn. Measured on the emulator: `drawingFinished` followed the frame of the new size at every rotation.
- **No crash in the iOS simulator after a few frames** ([docs/porting/gpu-rendering.md](docs/porting/gpu-rendering.md), "The iOS simulator"): Skia turns framebuffer fetch on for the Apple GPU family the simulator's Metal device reports, the simulator's Metal compiler rejects it, and Graphite crashed on the pipeline it could not make. Since the GPU route of the lights and the pixel operations (#456), whose blenders read their destination, the prewarm of a context's second frame drew them, so every application crashed in the simulator. On a GPU surface of the simulator these effects are drawn by the CPU path and the prewarm skips them; devices are not affected.
- **Resizing in the browser is cooperative**: no frame is shown stretched while a page is resized (an elastic band at every step of a resize). When the thread of the page renders, the top-level renders at once after it is resized, in the resize observer, which runs after the browser's layout and before its paint (`paint`, the synchronous commit of the compositor, as a paint request of a desktop window does). With a render thread the worker keeps committing its frames to the canvas directly (nothing waits for the page in the steady state). While the view is resized, the page shows them in an overlay at their own size: it copies the current frame when the resize starts, the worker hands it a copy of each frame (`createImageBitmap`), and the overlay is removed once the canvas has a frame of the final size ([docs/porting/browser-render-worker.md](docs/porting/browser-render-worker.md), "Cooperative resize", with the experiments behind the design). Measured on the Ferro Store: during a resize of 40 frames every paint showed the frame of the previous step stretched before, none after; the control catalog test checks it in the builds with and without threads.
- **Images scrolled back into view are not uploaded again in Skia** ([docs/porting/gpu-rendering.md](docs/porting/gpu-rendering.md), "The image textures of Ganesh"): the resource cache of the GPU context holds 128 MiB by default (`SkiaOptions::max_gpu_resource_size_bytes`, `DEFAULT_MAX_GPU_RESOURCE_SIZE_BYTES`), where it held upstream's 29.5 MB. A page whose images did not fit evicted the textures of those that scrolled out of view and uploaded them again when they came back: 52 uploads of 23 MB per two scrolls of the Ferro Store's Discover page in the browser, none now.
- **Reveal lighting on the GPU in Vello's hybrid and GPU modes** (#459, [docs/porting/gpu-rendering.md](docs/porting/gpu-rendering.md)): the scene lighting effect is evaluated per pixel by a render pass of FerroUI on the device (a WGSL port of the light math) into a pooled texture the scene paints with, instead of a light map sampled and uploaded on every paint. Steady frames allocate nothing; the light is within 2 levels of the exact light. The CPU mode keeps the light map (the reference); the other effects of Vello that are drawn on the processor are listed with their GPU route in the same document.
- **No software masks for rounded clips in Skia** (#457, [docs/porting/gpu-rendering.md](docs/porting/gpu-rendering.md)): a clip of a rounded rectangle that Ganesh cannot apply analytically (under a rotation or a skew, with complex corner radii, or nested in another rounded clip, which Ganesh merges into a rounded rectangle with different corners) was rasterized on the CPU into an A8 mask and uploaded each time the element moved (the single-channel uploads measured while scrolling the Ferro Store on WebGL2). On GPU surfaces such a clip is now a clip shader evaluating the coverage of the rounded rectangle per pixel; single upright clips stay analytic clips, and the raster backend keeps Skia's clip. The coverage is within 14 levels of the exact area at the edge (2 to 4 on average). A GPU render target also prewarms the programs of the runtime effects with its second frame, so the first frame that uses one does not wait for the GPU to link it.
- **Scrolling through images in the browser** (the Vello backend): a texture of an image that is no longer drawn is kept while the textures of images fit 128 MiB (the ones drawn the longest ago released first, any not drawn for 3600 renders released), where it was released 16 renders after the image left the scene. Content that scrolled out of view and back was uploaded again, a copy and premultiplication of every pixel in the module and a texture upload per image, which on a phone made a fast scroll through a page of screenshots run at 20 frames a second. The WebGL2 renderer, the hybrid and the GPU mode share the rule (`scene/image_textures.rs`).

(`ferroui-markup-xaml`);

The first preview of 0.4. It adds:

- **Vello performance**, rounds 1 to 5 and an experimental round (#263 to #268), on the published Vello crates without patches:
  - rectangles and rectangle clips drawn by the renderers' own paths; text of the hybrid mode from its glyph atlas;
  - the CPU mode keeps its render contexts, renders kept targets and windows only where they changed, renders large scenes on the thread pool of `vello_cpu`, and keeps the pictures of box shadows;
  - the GPU mode draws its filters on the device and renders kept targets only where they are cleared;

  - a depth buffer for the hybrid renderer, so opaque content is drawn front to back; the Metal queues ordered by a shared event instead of a wait on the processor;
  - `FERROUI_FRAME_TIMES`, and benchmark and profiling scripts (`scripts/vello-perf`).

The GPU mode of Vello uses it. The deviation is recorded in `docs/porting/DEVIATIONS.md`.

### Known limitations

- **No reconciler yet.** A component runs once; what changes later is changed through signals and the children that follow state. Running a component again and comparing its element trees is the next phase ([docs/declarative-ui.md](docs/declarative-ui.md), section 8).
- **Builders for the controls of `ferroui-controls` only.** The TreeDataGrid, the colour picker and other crates of controls are used through `Element::Existing` until the generator covers them.
- **Vello stays optional.** Skia is the default backend. On a real GPU, a full redraw (scrolling, a page drawn again) is still slower with Vello than with Skia. Vulkan and Direct3D 12 were tested in software only, not on hardware.
- The limitations of 0.3.0 below still apply.

- **Items sources from the reactive libraries**: the `ObservableCollection` of `ferroui-system` is an items source of the controls, as in .NET, so a collection that DynamicData's `sort_and_bind` or `bind` fills (`ObservableCollectionExtended::collection()`) is shown by a `ListBox` or an `ItemsControl` directly.
- **Port tracking for several references**: the port-status tooling tracks Rx.NET beside the framework (`docs/porting/tracking/reactive/`).

### Known limitations

- **One thread.** The observables, view models and subscriptions are single-threaded, as FerroUI's object model is. Work on another thread goes through `ferroui_system::threading::tasks::run` and comes back to the thread that started it; there is no thread-pool scheduler.
- **No reflection or expression trees.** Property paths (`prop!`) stand for the expressions of .NET. The `*Unsafe` overloads, `WhenAnyDynamic`, assembly scanning and the type-based APIs of Splat are not ported. The adapters of Splat and ReactiveUI to other dependency-injection containers are not ported either; a port of Microsoft.Extensions.DependencyInjection is tracked separately.
- **Types that wait for a later preview.** The binding converters of `DateTime`, `DateTimeOffset`, `DateOnly`, `TimeOnly`, `Uri` and `Decimal`, and the Rx and DynamicData tests that use `Decimal`, wait until those types move from `ferroui-base` to `ferroui-system`.
- Every difference from the reference libraries is recorded in `docs/porting/DEVIATIONS.md`, sections Reactive, DynamicData, Splat, ReactiveUI, ReactiveUI controls and Samples.
- The limitations of 0.2.0 below still apply.

- **TreeDataGrid**: an observer of a cell binding (`ICellBinding::subscribe`) takes the value by value, and `ITextCellOptions` adds `has_default_string_format`; a text cell no longer copies its text and its value again.
- **Translating a visual into the coordinates of one of its ancestors** (`Visual::transform_to_visual`, `translate_point`) walks up from the visual once, where it walked both visuals up to the root; the transforms of the visual tree and the effective viewport read the render transform only of visuals that have one; the layout queues and the scroll anchors of a scroll presenter keep their entries in maps with the Fx hasher. ## [0.1.0] - 2026-10-17

The first release that is not a preview. It is the fourth preview with the work that followed it: the port at upstream 66b7273b9a, the WinUI 3 theme placing text on the baseline of native WinUI 3, and touch scrolling that coasts after a flick, in the browser on a phone too. ### Added

- **`TextBlock.LayoutRoundingPlacement`** (`TextLayoutRoundingPlacement`: `Below`, the default, or `Above`), an inherited attached property of `TextBlock` and a FerroUI addition: where a text block puts the height that layout rounding adds to it. With `Above` the text, the selection and hit testing of `SelectableTextBlock`, the access key underline of `AccessText` and the embedded controls move down by that height, as WinUI's TextBlock places its text (`docs/porting/text-rendering.md`, section 6).

### Changed

- **Upstream 66b7273b9a.** The port follows upstream's 49 commits since 17350180 (`docs/porting/CONTINUATION.md`, hand-over of 2026-10-17): among them the immutable stream geometry builder (`IStreamGeometryBuilder`; the mutable stream geometry implementation is removed, its interfaces deprecated), text fixes (bidi after a reset and the run index of the reorderer, the ellipsis of wrapped text cut by a height or a line limit, the caret of centred text, empty text ranges, the text layout released on detach), styling and focus fixes, Wayland popup positions and application id, the 120 Hz display link on iOS, the headless window positioning options, AT-SPI headings, lists and children changes, and the rewritten pointers page of the ControlCatalog.
- **The WinUI 3 theme places text as WinUI 3 does**: its top-levels set `TextBlock.LayoutRoundingPlacement` to `Above`, which moves the text of the theme by up to one device pixel down to the baseline of native WinUI 3 (measured at 200 %: from 0.99 px above to 0.01 px). The Fluent and Simple themes keep the reference's placement and their pictures are unchanged.
- **The tabs of the WinUI 3 theme are as wide as each other**, as the tabs of WinUI's TabView in its default `TabWidthMode="Equal"`: the strip of a TabControl at the top or the bottom gives every tab the width of the strip divided by their number, between `TabViewItemMinWidth` (100) and `TabViewItemMaxWidth` (240), shrinks them as the strip narrows and scrolls them, with its scroll buttons, when they do not fit at the minimum width; a tab was as wide as its header. The width comes from `TabViewEqualWidthPanel`, a new primitive of the theme crate (`FerroUI.Themes.WinUI.Primitives`) and the items panel of the strip; the tabs at the left and the right stay stacked, and TabbedPage's top pane keeps items as wide as their content.
- **The development variable `FERROUI_TEXT_BASELINE_ROUNDING` is removed**; the property above replaces it, and a calibration run of the WinUI theme gallery sets the property with its key `baseline` (`below`, `above`, `theme`).

### Fixed

- **A touch flick scrolls on after the finger is lifted** (every touch platform, and the browser on a phone, where a swipe moved the content only as far as the finger): the inertia of the scroll gesture started its clock with its first frame, which therefore scrolled by nothing, and the scroll viewer, which chains scrolling by default, took that for the end of the content and ended the gesture. The inertia is timed from the release, as upstream; measured in Chrome with touch input at a phone's viewport, a flick of 200 px now scrolls the home page of the ControlCatalog by more than 630 px, where it scrolled by 195 px.
- **A touch flick scrolls on in a browser whose page draws slowly** (the page without threads on a slow phone): a pointer event of the browser is stamped with the time the browser raised it rather than the time the view handled it. The view handles input between the frames it draws, and a frame longer than 40 ms made a finger lifted while it moved look as if it had rested, so the scroll gesture got no speed to coast with.
- **Touching a text box on a phone no longer zooms the page in the browser**, which then could not be zoomed out after the keyboard hid: the hidden input element of the text input method has text of 16 px, the size mobile browsers do not zoom into (it had the default 13.33 px); the ControlCatalog page and the pages of the browser examples ask Chrome on Android to lay the view out in what the keyboard leaves (`interactive-widget=resizes-content`), and an offset a mobile browser leaves a page that cannot scroll at after the keyboard hides is undone.
- **A window follows a change of its text rendering from the next frame** (Skia backend): the layer the composition target keeps for a window whose frames are not kept (every GPU swap chain) kept the text contrast, gamma and subpixel order of the frame it was created in until the window was resized; it is now created again when they change, so a change of the system's ClearType settings, or a calibration override, reaches the window at once.
- **The WinUI 3 theme after the last comparison with native WinUI 3** (`docs/porting/winui-theme/DEVIATIONS.md`): the calendar is as tall as WinUI's, with its days where WinUI draws them (CDB-10); the text of CalendarDatePicker starts where WinUI's does and its calendar glyph has the size and the shape of the native one (CDP-2, CDP-3); the shadows of menus, context menus, flyouts, tool tips and the date and time picker flyouts are drawn, which the presenters clipped away as templated controls (G-24); the path icons of menu items are as large as WinUI's (12 px of a 24-unit geometry where they were 16, PI-3); the elements of the templates that draw a background and a border draw the background inside the border, WinUI's default, so that translucent strokes such as the borders of the notification cards are drawn over the page (G-25).
- **The text calibration page of the WinUI theme gallery** has the layout of its native twin: its grid is aligned to the top, as tall as its rows, where the stretched grid gave each row one more device pixel under layout rounding and moved the lower rows by up to 11 px at 200 %.

### Known limitations

- **Verification.** Every platform was verified in continuous integration, in virtual machines, in the iOS simulator and on the Android emulator; not on a range of real devices.
- **The Vello backend** is experimental (`docs/porting/vello-backend.md`, section 13).
- **XAML**: hot reload and parts of the build integration are open.
- **The browser platform**: the scripts that assemble a site are in the repository and not in a package (`docs/release.md`, section 6.1).

- **Skia with Vulkan on Windows is built by a workflow of its own** (`skia-vulkan-windows.yml`, by hand and weekly): the feature `vulkan` of `ferroui-win32` compiles Skia from source.

- **Android builds with stable Rust.** The native library of an application no longer needs a nightly toolchain, `-Zbuild-std` or unstable flags: the framework keeps its thread-local variables in one table per thread on Android instead of one key of the C library per variable (of which the system has 128 for a process), and a library takes 9 keys (`docs/porting/android-platform.md`, section 5.1). `scripts/android/apk.sh` builds with the stable toolchain and the target `aarch64-linux-android`.
- **One loader of the libraries opened at run time** on Linux (`ferroui-base`): `ferroui_base::platform::native_library` (`NativeLibrary`, `native_functions!`) is shared by the X11, Wayland and Linux framebuffer crates, which had loaders of their own. Their behaviour is unchanged.
- **The text view visual of an input method client is optional** (`ferroui-base`, `ferroui-controls`): `TextInputMethodClient::text_view_visual` returns an `Option`, as upstream's value is nullable.

### Fixed

- **A text box without a template** panicked when it got or lost the focus with an input method active; it takes the focus now (`ferroui-controls`).
- **A popup opened while its target is moved by a render transform** (a page that slides in) stayed where the target was at the opening; an open popup is positioned again when the transform of its target changes (`ferroui-controls`; an upstream defect, recorded in `docs/porting/DEVIATIONS.md`, Popup).
- **The children of a border with a box shadow in a render target bitmap of more than 96 DPI** were drawn at twice their size and away from their place; the transform of a drawing context after a restore is the logical one again (`ferroui-skia`; an upstream defect, recorded in DEVIATIONS).
- **The render timer of the macOS native library** stops its display link when it is destroyed; a tick at the exit of the process read the freed timer (`ferroui-native`).

### Known limitations

- **Verification.** The new platforms and modes were verified in CI, in virtual machines, in the iOS simulator and on the Android emulator, not on real devices, boards or GPUs; no screen reader was run on any platform. The per-platform documents under `docs/porting` say what was run where.
- **WinUI.** Input, the input method, drag and drop and a client of UI Automation inside a WinUI 3 application are not verified (`docs/porting/winui.md`, section 9).
- **Wayland.** Opt-in, as upstream: the platform detection chooses X11. Not verified on a desktop compositor with input, with a real input method, or with the dmabuf swap chain on a GPU.
- **OpenGL on macOS and iOS** needs Skia built with `RUSTFLAGS="--cfg ferro_skia_apple_ganesh"`; the default build draws with Graphite on Metal.
- **Vulkan on Windows** compiles Skia from source (the feature `vulkan` of `ferroui-win32`).
- **Markup.** The build-time compiler of markup does not have the manifest keys, `include_xaml!` per class, the generated `register_types` or the diagnostics and cache of the build yet (`docs/porting/xaml.md`, 9.10.1).
- **API stability, the Vello backend, documentation.** As for the first preview.

## [0.1.0-preview.1] - 2026-10-15

The first preview.

The preview makes the framework available as crates so that it can be tried outside the repository. It is not a stable release: the public API is not settled, several subsystems are incomplete, and the per-subsystem state is tracked in [docs/porting/CRITICAL-PATH.md](docs/porting/CRITICAL-PATH.md).

### Added

- **Object model and base library** (`ferroui-base`): styled and direct properties with value priorities, inheritance, coercion and change notification; logical and visual trees; routed events; layout; input, focus and gestures; styling, control themes, resources and theme variants; data binding; animation and transitions; the media object model, fonts and text layout; the compositor with its render loop and dirty-region tracking.
- **Controls** (`ferroui-controls`, `ferroui-controls-color-picker`, `ferroui-dialogs`): the application model, top levels and windows, most of the control set including items controls, text input, menus, pickers, calendar, pages and automation peers; the colour picker library; the managed file chooser and the about dialog.
- **Themes** (`ferroui-themes-fluent`, `ferroui-themes-simple`, `ferroui-fonts-inter`): the Fluent and Simple themes for every ported control, in light and dark variants, and the embedded Inter font collection.
- **Markup** (`ferroui-markup`, `ferroui-markup-xaml`, `ferroui-markup-xaml-loader`, `xamlx`, `ferroui-build`, `ferroui-build-scan`): binding paths, the XAML run-time library and markup extensions, the run-time XAML loader, and the compilation of markup documents to Rust source by the build script of a crate.
- **Rendering and text** (`ferroui-skia`, `ferroui-harfbuzz`, `ferroui-opengl`, `ferroui-metal`, `ferroui-vello`): the Skia render backend (Graphite on Metal; Ganesh on OpenGL, on ANGLE and on WebGL; raster), HarfBuzz text shaping, the OpenGL and Metal platform contracts, and the Vello render backend.
- **Platforms** (`ferroui-desktop`, `ferroui-native`, `ferroui-microcom`, `ferroui-win32`, `ferroui-x11`, `ferroui-freedesktop`, `ferroui-ios`, `ferroui-android`, `ferroui-browser`, `ferroui-headless`):
  - macOS: windows, input, clipboard, drag and drop, menus, tray icon, Metal and software surfaces.
  - Windows: windows, input including pointer and touch, clipboard and drag and drop over OLE, icons, the task bar, the tray icon, file dialogs, mounted volumes, platform settings, the native control host, the extended client area; rendering in software, through ANGLE and through DirectComposition.
  - Linux on X11: windows, input, input methods (XIM, IBus, Fcitx), clipboard, drag and drop, screens, the desktop portals (settings, file chooser), GTK file dialogs, menus and the tray icon over D-Bus, session management, the native control host and XEmbed, accessibility over AT-SPI; rendering in software, with the shared memory extension, through GLX and through EGL.
  - iOS: a view over Metal, touch, keys and text input, platform settings, clipboard, storage, the native control host, accessibility.
  - Android: a view over a surface with EGL or software rendering, touch, keys and the input method, lifecycle, clipboard, storage, the native control host, accessibility.
  - The browser platform on `wasm32-unknown-emscripten`, and the headless platform for tests.
- **Tools** (`ferroui-designer-support`, `ferroui-remote-protocol`, `microcom-codegen`): the previewer and its remote protocol, and the code generator of the interop runtime.
- **Reserved names** (`ferroui`, `ferroui-wayland`, `ferroui-vulkan`, `ferroui-linuxframebuffer`, `ferroui-winui`, `ferroui-headless-vnc`): empty placeholder crates for parts that do not exist yet. They hold no code; a later preview replaces each with the real crate.

### Known limitations

- **Platforms.** macOS and the browser are the most complete. Windows, Linux (X11), iOS and Android are new in this preview and less tested: they were verified on the runners of the continuous integration, in virtual machines, in the iOS simulator and on the Android emulator, not on a range of real machines, devices and desktops.
- **Windows.** No input method (IME) support yet: ordinary typing works, composition for languages that need it does not. No UI Automation (accessibility), no WGL, and the blur, acrylic and mica transparency levels are reported as unsupported.
- **Linux.** X11 only: Wayland, the Linux framebuffer and Vulkan are not ported. Accessibility over AT-SPI was verified against the registry of at-spi2-core, not with a screen reader.
- **iOS.** Verified in the simulator only; no signed device build is described. Accessibility was not verified with VoiceOver.
- **Android.** Verified on the emulator (API 36) only. An application for Android cannot be built with stable Rust for now: the native library needs a nightly toolchain with a rebuilt standard library, because the standard library of the stable Android targets takes one thread key per thread-local value and the system has 128 (`docs/porting/android-platform.md`, section 5.1). Accessibility was not verified with TalkBack.
- **API stability.** None. Names, signatures and crate boundaries may change between previews, and the crates of one preview work only with one another (they are pinned at the exact version).
- **Vello backend.** Experimental. Skia is the default backend and the reference; the Vello backend is measured against it and does not yet match it everywhere (see `docs/porting/vello-backend.md`).
- **Compositor.** Composition animations and custom visuals are incomplete.
- **macOS platform.** Storage dialogs and parts of accessibility are incomplete.
- **Markup.** The run-time loader passes the ported test suites with a small number of documented gaps; the compiler of markup to Rust source is used by the themes and the samples.
- **Build requirements.** The Skia backend downloads a prebuilt Skia at build time, or builds it from source when no prebuilt binary matches the target and features, which needs network access and can take a long time. HarfBuzz is built from source and needs a C++ compiler. The macOS platform compiles an Objective-C++ library and needs the Xcode command line tools. The Windows platform needs the MSVC build tools, and `libclang` for its default feature `angle`. The Linux platform opens its system libraries (Xlib, GTK, GLib, the session management libraries) at run time and links none of them. The browser platform needs Rust 1.93 or later, Emscripten and the matching `wasm-bindgen` command-line tool (see `docs/porting/browser-platform.md`).
- **Documentation.** The API documentation is the documentation comments carried over by the port; there are no guides beyond the README and the documents under `docs/`. Not every crate is expected to build on docs.rs (see `docs/release.md`).
- **Tests of the published crates.** The packages hold the sources of the tests but not the test fonts and images of the Skia backend; the test suites are run from the repository.
